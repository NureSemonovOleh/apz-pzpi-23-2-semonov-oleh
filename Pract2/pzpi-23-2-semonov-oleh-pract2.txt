3 ОПИС ВИКОНАНОЇ РОБОТИ
3.1 Загальні відомості про систему
Назва системи: X (до 2023 року — Twitter).
Розробник: X Corp. (до жовтня 2022 року — Twitter, Inc.; заснована Джеком Дорсі, Ноа Глассом, Бізом Стоуном та Еваном Вільямсом у 2006 році).
Призначення системи: мережа мікроблогів та соціальної взаємодії, що забезпечує публікацію коротких повідомлень, обмін медіаконтентом, участь у публічних дискусіях та поширення новин у реальному часі. Область застосування — засоби масової інформації, маркетинг, цифрові комунікації, суспільно-політичний дискурс. Понад 250 мільйонів активних користувачів щодня публікують близько 500 мільйонів повідомлень, а в пікові моменти (трансляції, глобальні події) платформа обробляє понад 6 000 твітів на секунду.
3.2 Архітектурний стиль системи
X використовує гібридний архітектурний стиль, що поєднує мікросервісну архітектуру, подієво-орієнтовану архітектуру та клієнт-серверну архітектуру. 
Мікросервісна архітектура прийшла на зміну початковому монолітному застосунку на Ruby on Rails (2006), пройшовши через проміжний етап сервіс-орієнтованої архітектури (SOA, ~2010). Сьогодні окремі сервіси відповідають за створення та отримання твітів, управління профілями користувачів, формування стрічки новин, пошук у реальному часі та надсилання сповіщень. Кожен сервіс масштабується та розгортається незалежно, що дозволяє ефективно справлятися з нерівномірним навантаженням на окремі функції системи. 
Подієво-орієнтована архітектура керує асинхронною взаємодією між сервісами через брокер повідомлень Apache Kafka. Публікація нового твіта породжує ланцюжок подій: Timeline Service отримує подію та поширює твіт у стрічках підписників, Notification Service формує сповіщення, Search Service індексує вміст. Такий підхід дозволяє залишатися системі чуйною, навіть коли одночасно публікуються мільйони твітів.
 Клієнт-серверна архітектура забезпечує взаємодію між веб-, мобільними застосунками та API-клієнтами з бекендом через єдиний шлюз. На боці клієнта реалізовано кешування нещодавно переглянутого контенту та механізми оптимістичного оновлення інтерфейсу.      Гібридний підхід обрано для вирішення трьох критичних викликів: масштабованості до мільярдів подій на добу, забезпечення затримки відповіді менше 100 мс та автономності розробки і розгортання окремих сервісів.
	3.3 Основні компоненти системи
Користувач має можливість користуватись системою за допомогою двух джерел. 
Веб -застосунок реалізовано на основі React, що забезпечує динамічне оновлення стрічки без перезавантаження сторінки. Розробникам надається доступ до Twitter API v2 через REST-інтерфейс для інтеграції сторонніх застосунків.
Мобільна взаємодія реалізована через нативні застосунки для iOS та Android, що дозволяють ефективно використовувати можливості пристрою: камеру, сповіщення операційної системи та жести навігації. 
3.3.2 Серверна частина
Основу бекенду складають сервіси, написані переважно на Scala та Java з використанням власного RPC-фреймворку Finagle, розробленого Twitter. Finagle забезпечує відмовостійку та ефективну взаємодію між сотнями внутрішніх сервісів. API Gateway на базі Nginx виконує функції первинної маршрутизації запитів, автентифікації та балансування навантаження.
3.3.3 Рівень бізнес-логіки
Бізнес-логіку реалізовано у вигляді спеціалізованих мікросервісів: Tweet Service відповідає за збереження та отримання твітів; User Service управляє профілями, підписками та автентифікацією; Timeline Service формує персоналізовані стрічки новин; Search Service забезпечує пошук у реальному часі на основі власного рушія Earlybird (побудованого на Apache Lucene); Notification Service надсилає push-сповіщення та електронні листи; Media Service обробляє завантажені зображення та відеофайли. Взаємодія між сервісами відбувається через Finagle/Thrift для синхронних запитів та через Apache Kafka для асинхронного обміну подіями.
3.3.4 Рівень зберігання даних
Система використовує комбінований підхід до збереження даних, обираючи оптимальну технологію для кожного типу інформації. 
MySQL з рушієм MyRocks (оптимізований варіант RocksDB) слугує основним реляційним сховищем для метаданих твітів та профілів користувачів. MyRocks обрано через кращу компресію даних та ефективніші операції запису порівняно зі стандартним InnoDB. 
Manhattan — власна розподілена сховище типу «ключ-значення», розроблена в Twitter. Використовується для зберігання стрічок користувачів, соціального графу підписок та особистих повідомлень. Manhattan забезпечує лінійне горизонтальне масштабування та реплікацію між дата-центрами. 
Redis виконує роль кешу для стрічок найактивніших користувачів, лічильників (лайки, репости), а також для тимчасового зберігання сесійних токенів. Hadoop/HDFS застосовується для аналітики, пакетної обробки даних та навчання алгоритмів рекомендацій.     
 Blobstore — об'єктне сховище для медіафайлів (зображення, відео, GIF),  доступ до яких надається через глобальну мережу CDN.

3.3.5 Допоміжні сервіси
Стабільність та продуктивність платформи підтримується такими інструментами: 
Apache Kafka виконує роль хребта подієво-орієнтованої архітектури, передаючи мільярди подій на добу між мікросервісами (публікації, лайки, репости, перегляди). 
Zipkin — система розподіленого трасування, що дозволяє відстежувати запит через ланцюжок мікросервісів та виявляти вузькі місця продуктивності.
Kubernetes та власна система оркестрації Aurora (на основі Apache Mesos) керують розгортанням та масштабуванням контейнерів сервісів.
3.4 Взаємодія компонентів 
Зовнішні клієнти взаємодіють із системою через REST API v2 (для публічних операцій) та WebSocket (для отримання твітів у режимі реального часу). Внутрішня взаємодія між сервісами відбувається через Finagle/Thrift для синхронних RPC-викликів та через Kafka для асинхронних подій. 
На рисунку 3.1 показано, як різні рівні системи X (Twitter) інтегровані між собою: 
 «Client Level» – веб-інтерфейс (React) та мобільні застосунки. Медіаконтент завантажується безпосередньо через Edge CDN; 
«Edge / Delivery» – API Gateway (Nginx) здійснює перевірку лімітів (Rate Limiting), автентифікацію та маршрутизацію запитів; 
«Service Level» – мікросервіси на Scala/Java (Tweet, Timeline, User сервіси), що координують бізнес-логіку; 
«Storage Level» – реляційні та NoSQL сховища (MyRocks, Manhattan), а також швидкий граф-кеш для зв’язків.
 
Рисунок 3.1 – Компонентна діаграма 
На рівні клієнтів веб- та мобільні застосунки надсилають запити через Load Balancer до API Gateway, який перевіряє авторизацію та маршрутизує запити до відповідних мікросервісів. Медіаконтент (зображення, відео) клієнти отримують напряму через CDN, минаючи бекенд. Timeline Service звертається до Redis Cache для отримання вже сформованих стрічок, і лише у разі кешу-промаху — до Manhattan.  
Ключовим архітектурним рішенням є алгоритм Timeline Fanout, що вирішує проблему поширення твіту серед підписників. Система застосовує гібридну стратегію: 
а) для звичайних авторів (менше 100 тисяч підписників) застосовується модель Push (fanout on write) — твіт одразу  записується у стрічки всіх підписників у Redis;
     	б) для «знаменитостей» (більше 100 тисяч підписників) застосовується модель Pull (fanout on read) — твіти підтягуються та змішуються зі стрічкою у момент запиту  користувача.
Такий підхід дозволяє уникнути перевантаження системи записами, коли впливова особа публікує твіт для десятків мільйонів підписників одночасно.
На рисунку 3.2 показано діаграму послідовності для процесу публікації твіта — від натискання кнопки до розповсюдження у стрічках підписників.
 
Рисунок 3.2 – Діаграма послідовності публікації твіта
Після натискання кнопки «Опублікувати» мобільний застосунок надсилає POST-запит до API Gateway. Tweet Service зберігає твіт у MySQL зі статусом «published» та публікує подію TweetCreatedEvent до Kafka. Клієнт отримує відповідь 201 Created не чекаючи на завершення fanout. Kafka асинхронно доставляє подію до Timeline Service, який виконує поширення твіта у стрічках підписників відповідно до гібридної стратегії [додаток В.1].
3.5 Масштабованість та надійність
3.5.1 Балансування навантаження
Вхідний трафік розподіляється на двох рівнях. На мережевому рівні (L4) відбувається первинний розподіл TCP-з'єднань. На прикладному рівні (L7) Nginx аналізує HTTP-запити та направляє їх до відповідних сервісів або дата-центрів, враховуючи географічне розташування користувача та поточне навантаження.
3.5.2 Відмовостійкість
Кожен мікросервіс функціонує автономно, тому збій у Search Service не впливає на можливість публікації твітів. Finagle реалізує шаблон Circuit Breaker: якщо залежний сервіс не відповідає, виклик переривається одразу замість очікування тайм-ауту, що запобігає каскадним збоям. Система застосовує принцип Graceful Degradation — у разі недоступності сервісу рекомендацій користувачу показується хронологічна стрічка.
3.5.3 Реплікація
Manhattan та MySQL використовують схему Master-Replica: основний вузол обробляє операції запису, а численні репліки обслуговують запити на читання. Дані реплікуються між декількома географічно розподіленими дата-центрами, що забезпечує відмовостійкість на рівні регіону та зменшує затримку для глобальних користувачів.
3.5.4 Кешування
Redis використовується для агресивного кешування стрічок найактивніших користувачів та лічильників (кількість лайків, реpostів, переглядів). Лічильники оновлюються атомарно в Redis та асинхронно синхронізуються з основною базою через Kafka [додаток В.2]. Кешування CDN дозволяє обслуговувати медіаконтент без звернення до бекенду для більшості запитів.

3.5.5 Контейнеризація та хмарна інфраструктура
Розгортання сервісів здійснюється через Kubernetes та Aurora (на основі Apache Mesos). Система автоматично масштабує кількість екземплярів контейнерів відповідно до поточного навантаження — під час трансляцій великих подій нові екземпляри Timeline Service та Tweet Service запускаються автоматично, а після спаду активності — зупиняються.
3.6 Приклади програмної реалізації
Алгоритм гібридного Timeline Fanout, що демонструє логіку вибору між Push та Pull стратегіями залежно від кількості підписників автора, наведено у додатку В.1.
Фрагмент коду, що демонструє кешування твіту та атомарне оновлення лічильника лайків у Redis з асинхронною синхронізацією через Kafka, наведено у додатку В.2.
Приклад роботи з Apache Kafka — публікація та споживання події TweetCreatedEvent — наведено у додатку В.3. 
Приклад звернення до публічного Twitter API v2 для отримання твітів користувача наведено у додатку В.4.
